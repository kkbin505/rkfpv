# SC3336 at 60 fps: 1152x648 2x2 binning (experimental)

The SC3336 tops out at 30 fps at full resolution (2304x1296). With 2x2 binning
it reads the whole field of view as 1152x648 at up to 60 fps.

Status: works on the board, **not integrated into the image build or `fpv`**.

| | result |
|---|---|
| debug mode (no wfb), 1152x648 | 60.0 fps, ~3.1 Mbps, steady |
| FPV mode (WiFi card, wfb running) | ~54 fps, see "Open" |
| picture | clean on the ground station, text readable |

## What it takes

| piece | file | why |
|---|---|---|
| sensor mode | `luckfox/patches/kernel/0001-sc3336-1152x648-binning-mode.patch` | third mode in `sc3336.c`: 1152x648, 59.9 fps, 255 Mbps/lane |
| mode selection | `src/isp.c`, config key `sensor = 1152x648` | `rk_aiq_uapi2_sysctl_prepare()` only checks the size; rkfpv sets it on the sensor subdev |
| IQ file | `luckfox/iq-add-binned-lsc.py` | adds 1152x648 to the LSC tables; without it ALSC fails and AE runs to full exposure (white picture) |
| CSI host | `luckfox/patches/kernel/0002-mipi-csi2-mask-repeated-fs-fe-mismatch.patch` | masks a per-frame `fs/fe mis` error seen with the first register tables |

Both kernel patches apply at the SDK root (`git apply`).

`/etc/rkfpv.conf` for the mode:

```
size = 1152x648
fps = 60
sensor = 1152x648
```

`sensor = auto` (default) keeps 2304x1296 @ 30; nothing changes for it.

IQ file, once per image (input: the stock file, output: the one to install in
`/oem/usr/share/iqfiles/`):

```sh
luckfox/iq-add-binned-lsc.py sc3336_CMK-OT2119-PC1_30IRC-F16.json out.json
```

## Register table

Rockchip's RT-Thread driver (`drv_sc3336.c`) has a binned 640x480 @ 75 table;
the Linux driver for the sibling SC3336P (`sc3336p.c`) has 1152x648 @ 60. The
mode here is the RT-Thread table with the window opened to 1152x648 and these
values as in the SC3336P table: `0x36ec=0x2c` (255 Mbps/lane) with its MIPI
timing registers, `0x5900=0xf1`, `0x30b8=0x33`. Line length `0x320c/d=0x05a0`
(+3 % over the default) so one line fits at 255 Mbps; frame length 662 lines.

What went wrong on the way, for the next sensor:

| table | result |
|---|---|
| 640x480 table, window widened, default line length | 486 of 648 lines per frame (`csi size err`) |
| MIPI doubled to 510 Mbps/lane (`0x36ec=0x1c`) | all lines arrive, 60.0 fps, but the raw frames are corrupt: 16-pixel vertical stripes, a garbage band on the left |
| 255 Mbps/lane + longer line (current) | clean raw frame |

Frame rate and bitrate do not show a corrupt picture. Look at a raw frame:

```sh
v4l2-ctl -d /dev/video0 --set-fmt-video=width=1152,height=648,pixelformat=BG10 \
  --stream-mmap=3 --stream-skip=5 --stream-count=1 --stream-to=/tmp/raw.bin
```

(10-bit packed, 1536 bytes per line.)

## Open

- **FPV mode reaches ~54 fps, not 60**, and one boot stayed at 1-2 fps. The log
  has `ANALYZER:E:no free item for sofInfo!` and `CAMHW:E:frame losed`: AIQ's
  thread falls behind. Debug mode holds 60.0, `MemAvailable` in FPV mode is
  about 3 MB and any extra process (`v4l2-ctl`, even `grep`) lowers the frame
  rate, so memory is the suspect, not the encoder (44.8 MP/s here, 89.6 MP/s
  in the default mode). Untried: a smaller `rk_dma_heap_cma` (24M is sized for
  2304x1296).
- Indoors the picture looks soft and desaturated. Expected cause: exposure is
  capped at 16.7 ms, gain goes up, and the IQ file strengthens noise reduction
  and lowers saturation above 8x gain. Not confirmed with numbers; the `stats`
  line now prints exposure and gain for this (that change has not run on the
  board yet).
- The other IQ modules are calibrated for 2304x1296 and used as they are.
- Not in `mkoverlay.sh` / the image, not in `fpv` or the configurator; the
  test card got the four pieces by hand.
- Latency not measured.
